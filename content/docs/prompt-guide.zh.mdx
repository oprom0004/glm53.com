# 100 万 Token 极长上下文工程实践

传统大语言模型在面对 10 万字以上的长文本时，普遍面临“迷失在中间”（Lost in the Middle）与注意力稀释的痛点。

**GLM-5.3** 通过原生 **1,000,000 Token 动态 RoPE 扩展（YaRN 算法）** 与 **MLA（多头潜在注意力）**，在权威的 Needle-In-A-Haystack（大海捞针）测试中达到了 **99.8%** 的近乎完美召回率。

本指南总结了在百万字工业级工程中，如何正确组织 Prompt 上下文以获得最高确定性的输出。

---

## 长文本 Prompt 黄金结构原则

当您向 GLM-5.3 喂入整套代码仓库或数百页技术规范白皮书时，建议遵循 **“倒三角漏斗”** 的四层结构：

```
+-------------------------------------------------------------+
| Layer 1: System Invariants & Role Directive (系统恒定指令)    |
+-------------------------------------------------------------+
| Layer 2: Global Architecture Map / Index (全局索引与目录树)  |
+-------------------------------------------------------------+
| Layer 3: Massive Raw Context (百万字代码/规范/日志主体)        |
+-------------------------------------------------------------+
| Layer 4: Concrete Task Target & Output Contract (精准任务约定)|
+-------------------------------------------------------------+
```

---

### Layer 1: 系统恒定指令 (System Directive)
明确赋予模型严格的架构师角色，并规定约束边界（禁止臆测未出现的方法签名）：

```markdown
你是一位最高水准的分布式系统总架构师。你将审查以下整套代码仓库。
在给出任何修复建议前，你必须：
1. 引用代码中具体文件的行号；
2. 保持与现有工程类型系统严格一致；
3. 输出符合 standard `git diff` 格式的补丁。
```

### Layer 2: 全局代码拓扑图 (Global Architecture Map)
在装载具体代码文件前，先提供 200~500 行的**结构拓扑索引**。这能让 MoE 路由专家在预加载注意力时，建立全局模块依赖的图谱表征：

```markdown
<repository_structure>
├── core/
│   ├── engine.py       # 核心调度循环与任务队列
│   └── memory.py       # 跨节点共享显存驱动
├── network/
│   ├── rpc.py          # 基于 gRPC 的心跳与同步协议
│   └── buffer.py       # 环形零拷贝网络缓冲区
└── tests/
    └── test_deadlock.py # 并发压测回归用例
</repository_structure>
```

### Layer 3: 代码与文档主体 (Massive Raw Context)
使用明确的 XML 标签隔离各个文件，并标注完整路径：

```xml
<file path="core/engine.py">
# 文件内容...
</file>

<file path="network/buffer.py">
# 文件内容...
</file>
```

### Layer 4: 精准任务约定 (Task & Output Contract)
**极其重要**：务必将具体的问题或任务放在百万字上下文的**最末尾**，不要放在最前面！

因为解码器在生成第一个 Token 时，注意力会最直接锚定靠近末尾的指令，并顺着 KV Cache 回溯中间的大规模内容：

```markdown
<instruction>
请仔细分析 `network/buffer.py` 中的环形缓冲区在单生产者多消费者（SPMC）高并发模式下，
是否存在因内存屏障缺失导致的 ABA 竞态漏洞。
请给出证据并生成修复该漏洞的最小补丁。
</instruction>
```

## 避免幻觉的四大高阶技巧

1. **强行要求思维链（CoT）推理先于代码生成**：
   在输出代码前，要求模型显式输出 `<thinking>` 标签，列出依赖链与推演步骤，这能使 MoE 的逻辑专家集群被充分激活。
2. **给模型“不知道”的安全出口**：
   明确声明：“*如果在提供的 100 万字上下文中未包含对应接口定义，请明确声明‘上下文未提供’，严禁自行假设外部接口签名。*”
3. **分层分治提取法（Map-Reduce Strategy）**：
   对于超大规模的多步审计任务，可以先让 Flash 极速版执行第一阶段的模块摘要抽取，再由 753B 旗舰版进行关键交叉点的最终推演。
4. **Git Diff 模式强制约束**：
   要求输出符合 `diff --git a/... b/...` 规范，便于直接通过 CI/CD 工具链或自动化测试沙盒执行 `git apply`。
